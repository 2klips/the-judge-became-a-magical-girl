<배경>
해커톤 예선을 진행한다, 해커톤 예선의 주제는 AI를 활용한 게임제작 이며,
 제출용으로 웹 미연시(비주얼 노벨) 게임을 만든다.
심사는 [현장 시연 / 영상 / 링크 제출]이고, 플레이 데모 시간은 약 [10~30분]으로 한다,
지금 필요한 건 스토리가 아니라 게임 로직 설계다. 스토리와 컨셉, Asset은 로직이 확정된 뒤에 얹는다.
</배경>

<요청>
이 게임의 게임 로직 기획안을 작성해줘.
</요청>

<확정 사항 — 재논의 금지>
- 배포는 GitHub Pages. 정적 호스팅만 가능하고 자체 백엔드 서버는 없다.
- 플레이어 입력은 선택지 클릭이 아니라 STT를 활용한 음성으로 선택지를 고르거나 게임을 진행하는 것
이게 이 프로젝트의 핵심 차별점이다.
- 대화는 무한히 늘어지면 안 되고, 정해진 분기점으로 수렴해야 한다.
- 이 프로젝트는 모두 100% AI를 사용하여 제작하며 프로그래밍, Asset 모두 AI를 사용하여 제작한다.
</확정 사항>

<결정해야 할 핵심 갈림길>
두 방향 중 하나를 골라 권고해줘. 양쪽 장단점만 나열하고 끝내지 말 것.

A안: 저렴·저지연 LLM API(Gemini 2.5 Flash Lite 등)로 캐릭터가 자유 대화하고,
     턴마다 호감도/감정 스탯을 갱신해 임계치에서 사전 정의된 분기로 넘어간다.
B안: LLM 없이, 음성 인식 텍스트 + 오디오 특징(음높이·성량·발화속도 등)으로
     플레이어의 톤과 감정을 추정해 분기를 결정한다.

판단에 반드시 반영할 것:
- GitHub Pages에서 A안의 API 키를 어떻게 다룰지 결론을 낼 것
  (클라이언트 노출 감수 / 사용자 키 입력 / 외부 프록시 중 택1과 그 이유).
- 브라우저 음성 인식 API는 텍스트만 주고 운율 정보는 주지 않는다는 점.
  B안이 필요로 하는 감정 추정을 무엇으로 구현할지 명시할 것.
- A안 또는 B안으로 결정 될 경우, 시나리오&스토리 작가에게 어떤 식으로 [분기점, 스토리텔링, 선택지, 등]을 구성해야할 지
예시를 작성해줄 것
- 데모 환경에서 실패할 수 있는 요소(마이크 권한, 소음, 브라우저 호환성, 네트워크 지연)와
  그때의 대체 입력 경로.
</결정해야 할 핵심 갈림길>

<산출물>
- 상태 모델: 어떤 값을 들고 있고 언제 갱신되는지 (호감도/감정/플래그/턴 수)
- 대화 루프: 음성 입력 → 판정 → 캐릭터 응답 → 상태 갱신 → 분기 판정의 한 사이클 정의
- 분기 구조: 분기점 개수, 진입 조건, 엔딩 수와 도달 조건
- 대화 수렴 규칙: 턴 수 상한, 강제 전환 조건, 판정 실패 시 처리
- 데이터 포맷: 시나리오를 어떤 스키마(JSON 등)로 적을지, 예시 1개 포함
- 최소 기능 범위: 예선 제출에 반드시 있어야 하는 것과 잘라낼 것의 경계
- 화면 구성에 필요한 Asset 양식에 대해 자세하게 설명할 것
예 : 배경과 캐릭터 이미지, 캐릭터의 경우 표정만 여러개 제작해야 하는지, 자세를 제작해야 하는지 등
- 리스크와 대응

첫 문장은 A안/B안 중 무엇을 권하는지와 그 이유 한 줄로 시작할 것.
</산출물>

<작업 방식>
- 판단할 정보가 충분하면 바로 진행. 채택하지 않을 선택지를 길게 늘어놓지 말고,
  고민되는 지점은 목록이 아니라 권고로 제시할 것.
- 요청하지 않은 스토리, 캐릭터 설정, 아트 방향, UI 시안은 만들지 말 것.
- 확실하지 않은 API 동작이나 요금은 '확인 필요'라고 표시하고 추측으로 단정하지 말 것.
- 나만 답할 수 있는 정보가 필요하면 그때만 질문하고 턴을 끝낼 것.
</작업 방식>
