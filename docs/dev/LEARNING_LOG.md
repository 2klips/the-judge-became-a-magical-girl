# 프로젝트 인수 학습 기록

이 문서는 비개발자가 프로젝트를 인수하면서 변경 이유와 개발 개념을 이해하기 위한 보조 설명이다. 실제 수행 사실과 테스트 결과는 [IMPLEMENTATION_LOG.md](IMPLEMENTATION_LOG.md), 제품 계약과 기술 결정은 [DECISIONS.md](DECISIONS.md), 단계별 범위와 완료 기준은 [MILESTONES.md](MILESTONES.md)를 기준으로 한다. 이 문서는 단일 진실 공급원이 아니며 기존 문서 우선순위를 바꾸지 않는다.

## 기록 원칙

- 사용자 지시를 먼저 적고, 실제 변경과 신규 요소를 구분한다.
- 코드 이름만 나열하지 않고 왜 바꿨는지 쉬운 말로 설명한다.
- 비용·시간을 줄인 선택과 그 대가를 함께 기록한다.
- 사용자가 직접 확인할 파일과 화면을 연결한다.
- 확실한 사실은 `[확정]`, 제안은 `[제안]`, 사람 검수가 필요한 내용은 `[미결정]`으로 표시한다.
- 작업 결과와 학습 설명을 분리해 같은 사실을 여러 문서에 복제하지 않는다.
- 테스트 수치·완료 상태·미결정 항목은 복제하지 않고 해당 기준 문서로 연결한다.

## 프로젝트를 한 문장으로 설명하면

`심사역은 마법소녀가 되었다`는 브라우저에서 실행되는 음성·클릭 혼합형 비주얼노벨이다. 화면과 게임 규칙은 정적 웹앱이 담당하고, OpenAI가 필요한 음성·대화 판정만 Cloudflare Worker를 통해 호출한다.

## 왜 현재 구조를 유지하나

- 단일 `GameState`와 직렬 FSM은 진행 순서를 추적하기 쉽고 저장·복구 오류 범위를 줄인다.
- JSON과 zod 검증은 잘못된 대본 참조를 게임 시작 전에 발견한다.
- OpenAI Secret을 Worker에만 두면 공개 웹 코드에서 키가 노출되지 않는다.
- AI 장애가 나도 클릭·로컬 경로로 엔딩까지 갈 수 있어 시연 실패를 줄인다.
- 싱글 플레이 완성이 우선이므로 현재는 DB와 UI 프레임워크를 추가하지 않는다.

- `[확정]` 기준 날짜: 2026-08-10 KST
- `[확정]` 기준 브랜치: `main`
- `[확정]` 기준 커밋: `2a5821d8429d88208cb415b06992e7f6fe4dfabf`
- `[확정]` 원본은 저장소 밖 ZIP과 SHA-256으로 보관한다.
- `[확정]` 이후 구현은 최신 `origin/main`에서 만든 `codex/` 브랜치에서 수행한다.
- 정확한 보관 파일 수·체크섬·테스트 결과는 `IMPLEMENTATION_LOG.md`의 인수 기준점 항목에서 확인한다.

커밋 번호는 책의 판본 번호와 같다. 같은 번호를 가리키면 누구나 같은 코드 상태를 확인할 수 있다. ZIP은 사람이 열어보는 원본 사본이고, SHA-256은 그 사본이 바뀌지 않았음을 확인하는 지문이다.

## 2026-08-10 — 인수 원본 보관과 기록 체계

### 사용자 지시

현재 버전을 원본 파일로 별도 보관해 최종 버전과 비교하고, 이후 작업마다 무엇을 왜 수정했는지 초보자 관점으로 기록한다.

### 이번 작업을 이해하는 방법

- 일반 폴더 복사 대신 `git archive`를 쓰면 기준 커밋에 속한 파일만 재현할 수 있다.
- ZIP과 체크섬을 저장소 밖에 두면 비교 자료가 새 버전의 일부로 잘못 포함되지 않는다.
- 별도 브랜치와 worktree를 쓰면 원본 `main`을 유지한 채 문서 변경을 검토할 수 있다.
- 정확한 파일 수·체크섬·검증 명령 결과는 중복하지 않고 `IMPLEMENTATION_LOG.md`에서 확인한다.

### 이번에 배운 개념

- **커밋:** 특정 시점의 프로젝트 상태를 가리키는 Git 기준점이다.
- **브랜치:** 원본 흐름을 건드리지 않고 변경을 쌓는 독립 작업선이다.
- **worktree:** 같은 저장소의 다른 브랜치를 별도 폴더에서 여는 기능이다.
- **`git archive`:** 커밋에 포함된 원본 파일만 묶고 Git 내부 정보와 로컬 임시 파일은 제외한다.
- **SHA-256:** ZIP이 나중에 바뀌지 않았는지 확인하는 디지털 지문이다.
- **회귀 검사:** 새 변경 때문에 기존 정상 기능이 깨지지 않았는지 확인하는 검사다.

### 비교와 복구

- 코드 차이는 기준 커밋과 최종 커밋의 `git diff`로 확인한다.
- 원본 파일 자체는 별도 ZIP에서 확인한다.
- 작업 브랜치 문제가 생겨도 `main`과 원본 ZIP은 영향을 받지 않는다.

## 2026-08-11 — 논리 ID와 실제 이미지 파일 연결

### 주소록처럼 이해하기

게임 대본과 화면 코드는 이미지 파일명을 여기저기 직접 쓰지 않고 `transform.cast`, `gray_wraith.weakened` 같은 **논리 ID**를 사용한다. 논리 ID는 사람 이름, 에셋 catalog는 주소록, `assets/runtime/`의 파일은 실제 주소에 있는 집과 비슷하다.

이번에는 주소록과 방문 순서가 이미 준비돼 있었고 집만 비어 있었다. 그래서 코드나 시나리오를 고치지 않고 계약된 파일명으로 이미지를 넣는 것만으로 화면이 새 실파일을 찾을 수 있었다. 현재 주소와 상태의 기준은 [ASSET_MANIFEST.md](../assets/ASSET_MANIFEST.md)에서 확인한다.

### source와 runtime이 둘 다 필요한 이유

- `assets/source/`는 납품·추적용 보관함이다. 무엇을 전달받았는지 확인하고 나중에 다시 정규화할 때 쓴다.
- `assets/runtime/`은 게임이 실제로 읽는 진열대다. 규격과 용량을 통과한 채택본만 둔다.
- 두 파일의 디지털 지문이 같으면 보관한 채택본과 게임에 들어간 파일이 서로 바뀌지 않았음을 확인할 수 있다.

### 폴백은 왜 삭제하지 않나

실파일이 생겨도 폴백은 비상용 예비 타이어처럼 남긴다. 파일 로딩 실패나 배포 누락이 생기면 기존 이미지+CSS 또는 검은 화면으로 강등해 게임을 끝까지 진행하게 한다. 실파일은 정상 경로, 폴백은 사고 대응 경로이므로 서로 중복되는 기능이 아니다.

### 장면 순서가 이미지 품질보다 먼저인 이유

영창 장면에서 이미 변신 복장을 입으면 그림 자체가 좋아도 이야기 순서는 틀린다. 따라서 `변신 전 평상복 → 영창 시작 → 변신 완료 복장`처럼 캐릭터 상태가 사건 순서와 맞는지 먼저 확인해야 한다. 이것을 **상태 정합성**이라고 이해하면 된다.

### 같은 PNG인데 용량이 다른 이유

RGBA PNG는 모든 픽셀의 색과 투명도를 직접 저장한다. indexed PNG는 자주 쓰는 색을 색상표에 모아 번호로 저장하므로, 색 수가 제한된 캐릭터 이미지에서 훨씬 작아질 수 있다. 이번 작업은 캔버스와 투명 배경 계약을 유지하면서 저장 방식을 바꿔 용량 상한을 맞췄다.

정확한 파일 크기·테스트·커밋은 중복 기록하지 않고 [IMPLEMENTATION_LOG.md](IMPLEMENTATION_LOG.md)의 P0 항목에서 확인한다.

## 2026-08-11 — 그림 속 행동 관계와 화면 범위

### "있다"와 "하고 있다"는 다르다

사원증이 화면에 떠 있기만 하면 관객은 사원증과 도윤이 같은 장면에 있다는 사실만 안다. 도윤의 손가락이 사원증을 잡고 카메라 쪽으로 내밀면 누가 무엇을 하는지가 연결된다. 입이 보이는 발화 모양과 주노의 기도 자세까지 더해지면 두 인물이 함께 주문을 수행한다는 관계가 한 장에서 읽힌다. 이미지 검수에서는 물체의 존재뿐 아니라 **주체·동작·대상 연결**을 확인해야 하는 이유다.

### 화면 비율도 제품 범위다

가로 화면과 세로 화면은 같은 그림에서 보이는 영역이 다르다. 세로형 중앙 crop까지 지원하려면 핵심 요소를 좁은 안전 영역에 모으거나 화면 코드가 다른 crop을 사용해야 한다. 하지만 제품 범위에서 모바일을 제외하면 그 제약을 계속 최적화할 이유가 없고, 데스크톱 16:9에서 더 자연스러운 구도를 선택할 수 있다. 완료 기준은 절대 규칙이 아니라 사용자가 실제 제공하기로 한 화면 범위에 맞춰 바뀔 수 있다.

### 파일 교체가 안전한지 확인하는 법

`assets/source/`는 최종 채택본의 추적용 보관함이고 `assets/runtime/`은 게임이 읽는 복사본이다. 두 파일의 hash가 같으면 보관본과 실제 게임 파일이 정확히 같은 바이트임을 알 수 있다. 또 이전 hash를 거부하는 검사는 파일명이 같아도 옛 그림이 실수로 되돌아오는 일을 막는다.

정확한 파일 크기·hash·커밋·검증 결과와 남은 QA는 [IMPLEMENTATION_LOG.md](IMPLEMENTATION_LOG.md)의 `transform.cast` 데스크톱 포즈 수정 항목에서 확인한다.

## 2026-08-13 — 야근 시간과 그림의 연속성

### 창문과 조명도 이야기의 일부다

대사가 “늦은 밤”이라고 하는데 창밖이 낮거나 일몰이면, 독자는 같은 사건으로 받아들이기 어렵다. N0의 야근, N3~전투의 위협, N5의 변신이 모두 같은 밤에 일어나고, GOOD에서만 멈췄던 시간이 흐르며 아침빛이 들어와야 회복이 분명해진다.

### 동료를 멀리 두면 제작 비용을 줄일 수 있다

핵심 심사 팀은 장면에 남아 있지만 마법으로 시간·인식이 멈춰 있다. 이들을 멀리 작고 익명적인 실루엣으로 보이면 “보호해야 할 팀”은 전달하면서도, 사람별 얼굴·표정·동작 스프라이트를 새로 만드는 시간과 비용을 피할 수 있다. 대신 동료가 직접 행동하는 장면으로 바뀌면 별도 캐릭터 에셋이 필요하다.

### source와 runtime이 같은 바이트라는 뜻

`source`는 채택한 납품본의 추적용 보관함, `runtime`은 게임이 실제로 읽는 파일이다. 두 경로의 바이트와 hash가 같으면 정규화 후 채택한 파일이 배포용 경로에서 다른 파일로 바뀌지 않았다는 뜻이다.

### 시각 승인과 권리 승인은 다르다

사용자가 구도·빛·가시성을 보고 후보를 채택했다는 것은 “이 그림을 장면에 쓰자”는 미술 판단이다. 참조 이미지를 쓸 권한, 생성 서비스 플랜, 공개 배포 허용은 별도 증빙이 필요하다. 그러므로 이미지는 `ready`로 사용해도 최종 권리 승인 상태로 올리지 않는다.

정확한 변경 파일·커밋·검증 결과와 남은 데스크톱 QA는 [IMPLEMENTATION_LOG.md](IMPLEMENTATION_LOG.md)의 야근 연속성 항목을 따른다.

## 2026-08-14 — 음성 실패를 플레이 가능한 상태로 바꾸기

### 기술 오류와 플레이어 문구를 나누는 이유

`Failed to fetch`, HTTP 상태, HTML 응답은 개발자가 원인을 찾을 때 유용하다. 하지만 플레이어에게 그대로 보여 주면 무엇을 해야 할지 알기 어렵고 내부 공급자 정보까지 노출될 수 있다. 그래서 원래 오류는 진단에 보존하고, 화면에는 `권한`, `녹음`, `목소리 없음`, `시간 초과`, `서버`, `응답 형식`, `네트워크`처럼 복구 행동을 고를 수 있는 상태만 보여 준다.

### 한 번 실패와 계속 실패를 다르게 다루기

Wi-Fi 순간 끊김이나 짧은 발화 한 번 때문에 음성 모드 전체를 끄면 사용자는 원하지 않은 조작 방식으로 밀려난다. 첫 실패에는 같은 턴에서 한 번 더 말할 기회를 주고, 두 번째 실패에는 그 장면만 클릭으로 통과시킨다. 이런 실패 턴이 다섯 번 쌓였을 때만 전체를 클릭 모드로 바꾼다. 브라우저 자체가 녹음을 지원하지 않는 경우만 처음부터 클릭으로 우회한다.

### 공통 정책이 비용을 줄이는 방법

대화·변신 주문·전투가 각각 재시도 코드를 가지면 문구나 실패 횟수를 바꿀 때 세 곳을 따로 고쳐야 한다. 순수한 공통 정책 하나에 규칙을 두고 각 화면은 현재 턴 이름만 넘기면, 테스트 한 묶음으로 세 화면의 같은 동작을 보호할 수 있다. 개발 전용 실패 주입도 실제 typed failure 통로를 사용해 권한 설정이나 Worker 장애를 매번 손으로 만들 시간을 줄인다.

### 저장 설정과 새 기본값은 충돌하지 않는다

새 사용자는 BGM 20%로 시작하지만 이미 37%나 음소거를 선택한 사용자의 저장값은 유지한다. 기본값 변경은 아직 선택하지 않은 사람에게만 적용해야 설정을 존중하면서 첫 소리를 낮출 수 있다.

### 자동 검증이 사람 귀와 실제 장치를 대체하지 못하는 이유

테스트는 첫·두 번째·다섯 번째 실패 정책, raw 문구 차단, meter 상태, BGM 채널 수명을 빠르게 반복한다. debug 시각 preview는 화면 배치만 격리해서 보므로 실제 음성 capture를 누를 수 없다. 마이크 권한, 장치 연결, 실제 Worker 응답, 곡의 loop seam과 fade 청감은 브라우저·장치·헤드폰으로 별도 확인해야 한다.

정확한 테스트 수치, 재현 URL, Worker 상태, 아직 남은 수동 게이트는 [IMPLEMENTATION_LOG.md](IMPLEMENTATION_LOG.md)의 Wave 1 항목을 따른다.
